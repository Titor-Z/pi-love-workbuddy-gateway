# 模型覆盖表与冷同步设计

> 讨论来源：`DISC-20261015-2300`。属于「② `/v1/models` 补齐元数据 + 模型覆盖表」这一步。

---

## 0. 两条已定前提

1. **同步的是覆盖表，不是模型目录。** 目录是派生数据，随时能从上游重取；覆盖表是用户手写的源数据，只在编辑过的那台机器上。
2. **形态是「网关权威 + 客户端 dirty + 显式回推 + 三方合并」。** 不是自动双向合并，冲突必须由用户决定。

---

## 1. 为什么客户端要冷备而不是透传

`DISC-20261015-2300` 里一度想出「客户端原样透传网关的 `/v1/models`」，被否掉了，理由是使用场景：

- 电脑 B 外出时切到 gateway 模式，**没有 A 可以问**。这时它必须能独立给出模型列表。
- 这和 P1 凭证冷同步是同一条理由（外出即网关），不是新发明。

但**要冷的只有覆盖表**：B 切到 gateway 模式后本机有凭证，目录直接从 WorkBuddy 实时拉，不需要 A 给。缺的只有别名、免费截止、思考档位这些**只有用户能写**的东西。

这条区分把同步的数据量压到一张小 JSON，也让它和凭证同步的风险完全不在一个量级。

## 2. 覆盖表（源数据）

文件：`$XDG_CONFIG_HOME/piloveworkbuddy/model-overrides.json`

```json
{
  "revision": 7,
  "change_at": "2026-10-16T00:39:12+08:00",
  "models": {
    "glm-5.3": {
      "alias": "GLM 5.3（主力）",
      "free_until": "2026-10-31",
      "note": "下午便宜",
      "hidden": false,
      "thinking_level_map": { "off": null, "low": "low", "medium": null, "high": "high" },
      "updated_at": "2026-10-16T00:39:12+08:00",
      "updated_by": "a1b2c3d4e5f6"
    }
  }
}
```

| 字段 | 含义 |
|---|---|
| `revision` | 该文件被写的次数，**网关侧单调递增**。乐观并发的依据。 |
| `change_at` | 最后一次修改时间，**只给人看**。 |
| `alias` | 展示别名。替换展示名的第一段（费用标记仍由 `catalog` 拼在后面）。 |
| `free_until` | 免费截止日期。 |
| `note` | 人看的备注。 |
| `hidden` | 从列表里隐藏；**请求仍可用**，不拦。 |
| `thinking_level_map` | 直接就是 pi 的 `thinkingLevelMap` 形状。键是 pi 的档位，值是后端 `Efforts` 里的一个，`null` 表示不支持。 |
| `updated_at` / `updated_by` | 三方比对用。`updated_by` 是 device id。 |

关于时间戳（重要）：**它不是裁判。** 跨机器比时钟不可靠（时区、NTP、休眠），而且两台机器的时钟不构成一个次序关系。判据是**内容比较**（`local != base` 就是「本地改过」），时间戳只用于展示，以及同为「都改过」时的提示。

`thinking_level_map` 的取值由面板约束：**只能从该模型后端给的 `Efforts` 里选**，不允许手填。手填会送出一个后端不认的档位，表现为「pi 里选了 high，实际按 medium 跑」——这种错误不报错，只会静默错，必须从源头堵住。

### 与 `promotions.json` 的关系：取代它

`promotions.json` 的 `{free_until, note}` 就是覆盖表的子集。现在面板已经有一个 `/api/promotions` 编辑器，如果再开一个覆盖表，同一批字段会有两个写入口，必然漂移。

做法：**覆盖表取代 `promotions.json`，做一次性迁移**——读到旧文件且覆盖表不存在时导入，**成功才**把旧文件改名 `.migrated`（失败只告警、源文件不动）。这与 `journal` 分片迁移是同一套手法。

## 3. base 快照存哪

客户端存两份：

| 文件 | 内容 |
|---|---|
| `model-overrides.json` | 工作副本。本机编辑改的就是它。schema 与网关那份**完全一致**。 |
| `model-overrides.base.json` | 上次成功同步时**网关那一份的原样拷贝**（含它当时的 `revision`）。三方比对的共同祖先。 |

**dirty 不单独存标记**，派生得出：`dirty = (工作副本.models 深比较 ≠ base.models)`。少一个状态文件就少一处能漂移的地方。

同理：

- 本地改过 → `local != base`
- 网关改过 → `remote.revision != base.revision`

## 4. 三方合并算法

输入 `base` / `local` / `remote`，按 `models` 里每个 model id 逐项判定：

| 情况 | 结果 |
|---|---|
| 都没改 | 取 base |
| 只有本地改 | 取 local |
| 只有网关改 | 取 remote |
| 两边都改、内容相同 | 取任一 |
| 两边都改、内容不同 | **冲突**：列出来，用户逐项选（本机 / 网关） |
| 只在一边新增 / 移除 | 按上面同一张表判定 |

输出：合并后的 `models` 映射 + 冲突清单。合并结果由客户端算好推给网关，网关只做一次乐观并发检查（见下）——因为 base 只在客户端手上，网关不参与算合并。

**先只做 entry 级，不做字段级。** 同项冲突本来就少（不同机器改不同模型是常态），字段级合并的复杂度换不来对应的收益。真遇到再说。

## 5. 传输（relay 新增两个端点）

沿用已有的 PSK + TLS 通道：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/relay/v1/model-overrides` | 返回网关权威那一份（含 `revision`）。 |
| `PUT` | `/relay/v1/model-overrides` | body 含 `base_revision` + 合并后的 `models`。网关 `revision` 不是 `base_revision` 就返回 409，客户端重新拉取并再合并一次；成功则写盘、`revision + 1`。 |

### 这里放开了一条旧红线，必须写清

P1 定过「**不允许客户端推送**」，理由是「推送通道是新攻击面且违背网关唯一权威」。那是针对**凭证**说的，现在依然成立：

| | 凭证 | 覆盖表 |
|---|---|---|
| 是不是秘密 | **是**（账号令牌） | 不是（别名、日期） |
| 客户端能写吗 | **永远不能**。客户端一旦能刷新，多设备共享就退化成互相踢 | 能。离开网络期间的本地改动必须能回来 |
| 独立开关 | 有（默认关） | 跟随 relay 开关即可 |

所以：**「客户端不可写」是凭证专属的红线，不是全局红线。** 覆盖表是唯一放开的一处，放开的前提正是它**不含任何秘密**。这条要写进 CHANGELOG 与 README，避免被读成「网关可以随便被改」。

## 6. 面板（「模型」页）

表格每行一个模型，可编辑列：别名 / 免费截止 / 备注 / 隐藏 / 思考档位（下拉，选项来自后端 `Efforts`）。

客户端模式额外一块「同步」：

| 状态 | 显示 |
|---|---|
| 干净 | 已与网关一致（revision N） |
| 本机有改动 | 「本机有 K 处改动」+ 推回网关 |
| 网关有新版本 | 「网关有新版本，可合并」 |
| 冲突 | 逐项列出 base / 本机 / 网关三列，让用户选 |

## 7. 对下游的影响

- `catalog.Build` 增加覆盖参数：`alias` 替换展示名第一段、`free_until` / `note` 覆盖、`hidden` 过滤。
- 网关 `/v1/models`、面板 `/api/models`、面板 `/api/models/pi`、pi 插件的 `refreshModels`，**全部读同一份合成结果**，不再各自算一遍（客户端模式下各自重算会丢掉网关侧的促销信息，这是当前的真实缺陷）。
- `thinking_level_map` 原样进入 pi 的模型配置。

## 8. 测试

- 合并算法表驱动：都没改 / 只本地 / 只网关 / 都改成相同 / 冲突 / 新增 / 移除。
- `PUT` 的乐观并发：`base_revision` 不匹配 → 409。
- 迁移：`promotions.json` → 覆盖表，成功改名 `.migrated`，失败源文件不动。
- 客户端 dirty 派生：编辑前后 `dirty` 的翻转。

## 9. 明确不做

- 自动双向合并（冲突必须由用户决定——沿用「任何时候都不悄悄丢东西」）。
- 字段级合并（先 entry 级）。
- 同步模型目录（派生数据，实时拉）。
- 在客户端重新合成费用标记。

## 10. 落地后的两点澄清

- 客户端模式下**控制台照样能列出模型**：`Deps.Upstream` 在客户端模式就是
  `relay.Client`（只有未配对时为 nil）。原先担心的「目录属于网关那一侧」不成立——
  目录本来就是经 relay 实时取的，不需要客户端有凭证。
- **`revision` 的含义**：网关那份的 `revision` 是权威写次数；客户端工作副本也有
  自己的 `revision`，但**参与比对的是 `model-overrides.base.json`（共同祖先）里的那个**。
  本机没有改动时走 `Store.Adopt` 原样跟进网关注版本，不用 `Replace`——
  后者会把本机版本号推高，与网关越差越远，下次合并的基准就错了。
- 冲突不替用户决定，但给了两个显式的整体选边（「以本机为准」/「以网关为准」），
  外加「先不选，只报告」。逐条选择留到真有人需要时再做。
